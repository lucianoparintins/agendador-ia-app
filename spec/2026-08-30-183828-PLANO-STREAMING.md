# Plano: Streaming de tokens (`stream=True`)

## Objetivo
Permitir que `POST /chat` transmita os tokens da resposta do Ollama ao vivo (Server-Sent Events / SSE) quando `stream=true`.

## Decisões confirmadas
1. **Exposição:** flag `stream: bool = False` no `ChatRequest`; a rota `/chat` retorna `StreamingResponse` (`media_type="text/event-stream"`) quando `stream=True`.
2. **Rejeição:** transmite os tokens ao vivo; se a validação rejeitar o horário, o Ollama é reconsultado e é enviado um evento de **correção** final com a reply reprocessada.
3. **Persistência:** salvar apenas a **última** reply (a corrigida, se houve rejeição), mantendo o histórico coerente.

## Contexto
- O `/chat` atual chama o Ollama com `stream=False`, recebe a resposta completa, extrai o JSON do agendamento, valida contra a agenda (expediente, 1h fixa, conflito, passado) e — quando rejeitado — reprocessa com uma nova chamada não-stream para gerar `reply` amigável.
- Esse fluxo exige o texto completo, então a validação só pode ocorrer ao final; o streaming é "ao vivo primeiro, corrigir no fim".

## Mudanças por arquivo

### `app/schema.py`
- `ChatRequest`: adicionar `stream: Optional[bool] = False`.

### `app/ollama_client.py`
- Extrair a montagem das `messages` para um helper `_montar_messages(...)` para evitar duplicação entre os caminhos stream e não-stream.
- Novo método `stream_chat(historico, nova_mensagem) -> AsyncIterator[str]`:
  - `POST /api/chat` com `stream=True`;
  - `httpx.AsyncClient` + `client.stream(...)`;
  - `async for line in response.aiter_lines()`, parse dos objetos NDJSON e `yield` de cada `message.content`;
  - parar quando `done: true`.

### `app/main.py`
- Extrair helper `_processar_dados(sessao_id, dados, historico) -> (reply_final, agendamento, validacao)` com a lógica dos três ramos:
  - `confirmado` → salva com `status='confirmado'`, `validacao.valido=True`;
  - `insuficiente` → `status='rascunho'` (salva se houver algum dado), `validacao` com `motivo='insuficiente'`;
  - inválido (`data_invalida`/`hora_invalida`/`no_passado`/`fora_expediente`/`conflito`) → salva com `status='rejeitado'`, chama `ollama.reprocessar_rejeicao(...)`, retorna a nova reply como final.
  - A persistência da reply do assistente fica por conta do chamador, registrando apenas a reply final.
- Na rota `/chat`, quando `req.stream`:
  - retorna `StreamingResponse(gerador(), media_type="text/event-stream")`;
  - o gerador:
    1. abre `ollama.stream_chat(...)` acumulando o texto completo e emitindo `data: {"type":"token","content":...}` por pedaço;
    2. ao final, extrai o JSON dos dados acumulados e chama `_processar_dados(...)`;
    3. se a reply final diferir do texto transmitido (rejeição + reprocessamento) → emite `data: {"type":"correcao","reply":...}`;
    4. emite `data: {"type":"done","sessao_id":N,"agendamento":{...},"validacao":{...}}`;
    5. termina com `data: [DONE]`.

## Protocolo SSE
Cada evento é `data: <json>` seguido de linha em branco (`\n\n`):
- `{"type":"token","content":"<chunk>"}` — cada pedaço ao vivo.
- `{"type":"correcao","reply":"<texto corrigido>"}` — opcional, quando houve rejeição e reprocessamento.
- `{"type":"done","sessao_id":N,"agendamento":{...},"validacao":{...}}` — sempre, no final.
- Terminador `data: [DONE]`.

## Testes a validar (curl)
1. `curl -N` com `stream=true` e mensagem válida → eventos `token`, depois `done` com `agendamento.status=confirmado` e `validacao.valido=true`.
2. Mensagem sem data/hora → `done` com `status=rascunho`.
3. Horário conflitante / fora do expediente → `type=correcao` (reply corrigida) + `done` com `status=rejeitado` e motivo adequado.
4. Confirmar que apenas a reply final é gravada (`GET /sessoes/{id}/mensagens`).
